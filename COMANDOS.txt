-----------------------------------------------------------------------
  PUERTO 3000 OCUPADO  (conflicto con otro proyecto)
-----------------------------------------------------------------------
Ojo: el proyecto "pichanga" (Next.js) también corre en el puerto 3000.
Si está levantado, Kubo NO puede arrancar su backend.

Paso 1) Ver qué procesos escuchan en 3000:
  netstat -ano | findstr :3000
  -> última columna = PID

Paso 2) Identificar qué está corriendo cada PID:
  Get-CimInstance Win32_Process -Filter "ProcessId=<PID>" `
    | Select ProcessId, CommandLine | Format-List

Paso 3) Matar los procesos que no sean el backend Kubo actual:
  Stop-Process -Id <PID1>,<PID2> -Force

Paso 4) Confirmar que el puerto quedó libre:
  netstat -ano | findstr :3000
  (no debe devolver nada)

Paso 5) Relanzar el backend Kubo:
  cd backend
  npm run start:dev

Regla práctica: NO trabajar con Kubo y pichanga al mismo tiempo, o
cambiar uno de los dos a otro puerto.

-----------------------------------------------------------------------
  PASO 3-bis — APLICAR MIGRACIONES SQL  (NO ES AUTOMÁTICO)
-----------------------------------------------------------------------
Los .sql de backend/sql/migrations/ están montados en
/docker-entrypoint-initdb.d del contenedor mysql, y MySQL ejecuta ese
directorio UNA SOLA VEZ: únicamente cuando arranca sobre un directorio
de datos vacío.

  >> El volumen mysql_data sobrevive a `docker compose up -d --build`.
  >> Por lo tanto, en CUALQUIER BASE QUE YA TENGA DATOS —producción, o
  >> cualquier entorno que no se acabe de crear desde cero— las
  >> migraciones nuevas NO se aplican solas. Hay que ejecutarlas a mano.

No hay runner de migraciones: este paso es manual y es responsabilidad
de quien despliega.

Aplicar una migración (ejemplo con la 013 del portal de clientes):

  cd ~/kubo
  docker compose exec -T mysql \
    mysql -uroot -p"$MYSQL_ROOT_PASSWORD" kubo_devdocs \
    < backend/sql/migrations/013_portal_clientes.sql

Las migraciones son idempotentes (CREATE TABLE IF NOT EXISTS y ALTER
guardados con information_schema): reejecutar una ya aplicada no hace
nada. Ante la duda, se vuelven a pasar todas en orden.

Comprobar que quedó aplicada:

  docker compose exec -T mysql mysql -uroot -p"$MYSQL_ROOT_PASSWORD" \
    kubo_devdocs -e "SHOW TABLES LIKE 'client_users'; \
    SHOW COLUMNS FROM tickets LIKE 'created_by_client_user_id';"

Si se olvida este paso, el backend NO arranca: PortalSchemaValidator
comprueba el esquema al boot y aborta diciendo qué migración falta. Ese
aborto es deliberado — sin la 013, las entidades Ticket y TicketEvent
piden columnas que no existen y TODO el módulo de tickets (listado,
detalle, transiciones, asignación, SLA) responde 500. Se ve en:

  docker compose logs --tail=50 backend

  # Ver que todo quedó arriba
  docker compose ps
